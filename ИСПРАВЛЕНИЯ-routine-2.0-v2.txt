6.1 Допустимые адреса remote — точное равенство строк
Разрешены ровно:
  https://github.com/Ernyskaliry/Mirraylina.git
  https://github.com/Ernyskaliry/Mirraylina
  git@github.com:Ernyskaliry/Mirraylina.git
  ssh://git@github.com/Ernyskaliry/Mirraylina.git
- Нормализация: только снятие завершающего `\n` и `\r`. Регистр, `/` в конце, порт, логин, токен, query, fragment не нормализуются. Подстрока нигде не используется. В скрипте: `case "$1" in "<строка1>"|…) ;; esac`. В скрипте есть ещё один `grep -qx`, но он сравнивает целую строку sha коммита, а не адрес.
- Fetch: `git remote get-url --all origin` — каждая строка вывода должна пройти проверку.
- Push: `git remote get-url --push --all origin` — каждая строка должна пройти проверку. Git сам подставляет pushurl или url и применяет insteadOf/pushInsteadOf. В песочнице push-адреса должны быть ровно `no_push`, а fetch-адреса — по списку.
- Несколько адресов: проверяется каждый; хотя бы один не прошёл — СТОП.
- Неоднозначность: ошибка команды, пустой вывод или нет origin — СТОП с выводом команды (учётные данные замаскированы).
- Адрес с учётными данными (`https://x-access-token:…@github.com/…`) в список не входит, поэтому СТОП. Это безопасный вариант; вопрос вынесен пользовательнице. В диагностике часть между `//` и `@` заменяется на `***`.
- Известное из прошлой проверки (повторно не читалось): fetch-адрес настоящего хранилища — `https://github.com/Ernyskaliry/Mirraylina.git`, он проходит. Строки pushurl в увиденной части конфига не было, значит push-адрес совпадает с fetch-адресом. Это вывод из прежнего чтения, сейчас не проверялось.

6.2 Preflight (этап 0)
1) адреса fetch и push по 6.1; 2) `rev-parse --show-toplevel` = /workspace/vault-repo, ветка main; 3–4) `git status --porcelain` пустой, иначе СТОП без stash, reset, restore, checkout, clean, commit; 5–6) `git pull --ff-only origin main`, сбой → СТОП; 7) `git rev-parse HEAD` = `git rev-parse refs/remotes/origin/main` = sha из `git ls-remote origin refs/heads/main` (ровно одна строка `<40 hex>\trefs/heads/main`, иначе СТОП); 8) сохранить базовый HEAD и базовый sha remote (ls-remote).

6.3 Запись (этап 8)
Сначала проверки: HEAD = база, дерево чистое, ветка main, поля по контракту, путь в allowlist, источник допустим для пути. Затем точечные правки с чтением файла прямо перед правкой и дедупликацией по ключу, без удалений и перемещений. Потом `git status` (изменены только свои пути), `git add -- <путь>` по одному, `diff --cached --check`, `--name-status` (только A/M и allowlist), полный staged diff. Пустых коммитов нет; один коммит `git commit -m`.

6.4 Push и неизменность remote
1) Повторная проверка адресов по 6.1.
2) Pre-push sha = `git ls-remote origin refs/heads/main`. Он должен быть ровно одной строкой формата `<40 hex>\trefs/heads/main` и совпадать с базовым sha из Preflight. Если не совпал (ветку на GitHub изменили за время запуска) или ls-remote не удался — push нет, коммит остаётся локально.
3) `git push origin HEAD:refs/heads/main`.
4) Успех: ls-remote = `git rev-parse HEAD`, дерево чистое. Если ls-remote не удался или sha другой — «push не подтверждён», ничего не исправляется.
5) Отклонён: снова ls-remote.
   - sha совпал с pre-push sha → не больше одного повтора;
   - sha другой → повтора нет, стоп;
   - ls-remote с ошибкой → стоп.
   Без pull, rebase, merge и разрешения конфликтов, локальный коммит сохраняется, пользовательнице сообщается хэш и что коммит не отправлен.
Как определяется «remote не изменился»: строка sha из ls-remote побайтно равна сохранённой (pre-push или базовой). Локальная ссылка origin/main для этого не используется.
Ошибка ls-remote — всегда стоп: дальше без push и без повтора, коммит локально, причина в отчёте.

7. НЕОЖИДАННЫЙ STAGED DIFF
======================================================================
Поведение: немедленный стоп этапа 8. Коммит не создаётся, push не выполняется, ничего не откатывается. Не выполняются git reset, restore, checkout, clean, stash и другие команды, меняющие индекс или файлы. Всё остаётся как есть.
Отчёт пользовательнице (только команды чтения):
- ветка: `git branch --show-current`;
- базовый HEAD (из Preflight) и текущий: `git rev-parse HEAD`;
- изменённые, добавленные и удалённые файлы: `git status --porcelain=v1 --untracked-files=all`;
- staged diff: `git diff --cached --name-status` и `git diff --cached`;
- unstaged diff, если есть: `git diff --name-status` и `git diff`;
- причина остановки;
- «коммит не создан, push не выполнялся».
Следующий Preflight остановится на грязном дереве (шаг 3–4), пока пользовательница не разберётся.
Инструкция ей: посмотреть список файлов и сверить staged diff со списком запросов в отчёте; проверить, нет ли среди изменённых её собственных файлов. Решение за ней: например, проверить и закоммитить самой, отменить правки бота самой в своём Git-клиенте или Obsidian, или дать прямое указание. Способ автоматической очистки не предлагается.

Почему изменения вне allowlist не попадут в коммит (статический разбор последовательности; не тестировалось):
(а) Preflight пропускает только чистое дерево, поэтому чужих изменений и staged-файлов на старте нет.
(б) Этапы 1–7 и 6b только читают; если они что-то изменили, шаг 1 «Записи» (дерево чистое) это поймает до записи.
(в) Запрос с путём вне allowlist не применяется (шаг 2).
(г) Перед staging шаг 9 сверяет `git status` со списком своих путей; любой другой путь — стоп.
(д) `git add -- <путь>` только для явных путей из allowlist. Запрещены -A, ., -u, `commit -a` и pathspec-коммит.
(е) После staging `--name-status`: каждая строка должна быть A или M с путём из allowlist, иначе стоп.
(ж) `git commit -m` без -a коммитит только индекс, уже проверенный в (е).
Остаточный риск: hooks pre-commit в настоящем хранилище могли бы менять индекс. Наличие hooks я не проверяла (.git не читала, это запрещено). Вынесено в открытые вопросы.
